## Где мы

ИИ-инженер по авиационной технике. Пакеты `pdfprepare` (OCR, подготовка PDF) и `pdfgraph` (граф, поиск, ответы с машинной проверкой цитат). Сейчас в базе один тип ВС — Ми-8МТВ-1 (49 документов, 13 700 листов).

Закрыто: Фаза 0 (данные, флаги, дедупликация), Ф1.0 (векторный канал e5-small), Ф1.1 (RRF-слияние), Ф1.2 (аудит эталонов), Ф1.3а/б (гейты отказа), Ф1.4 (уточнения), Ф1.5/1.5.1/1.5.2 (ранжирование по конкретике, отказ по корпусному отсутствию, тип ВС по метке листа).

Рабочее дерево чисто по коду; единственное локальное изменение — `PROGRESS.md` (пользовательское, не трогать).

## Гейты отказа и уточнения (факты)

- Включены (`pdfgraph/gates.py`, `ENABLED_GATES`): **numbers, designators, aircraft_type**. Конкретика вопроса проверяется на листе-лидере; отказ — конъюнкция включённых, срабатывает раньше LLM-классификатора.
- Отклонён `rare_term` (df<1000): рубит 17 из 23 корпусных.
- Тип ВС проверяется по метке листа `pages.aircraft_type`, а не по вхождению строки в текст: упоминание Ми-26 в дополнении Д-1638 не делает документацию по Ми-26 доступной (Ф1.5.2).
- Десигнатор, которого нет ни на одном листе корпуса → отказ, не уточнение (Ф1.5.1).
- Clarify — только по гейт-пути: тема найдена, конкретика вопроса не подтвердилась на лидере. Слотless-вопросы не уточняются: форма вопроса не отличает полный от неполного (Ф1.4.1).
- CLI: код `0` — ответ и все цитаты подтверждены; `1` — отказ или неподтверждено; `2` — ошибка среды; `3` — требуется уточнение (цитат нет).

## Следующие задачи (по порядку)

1. **Десять оставшихся промахов поиска** (hit@5 0.6786 → выше): e04/e06 — сдвиг ранжирования, остальные восемь отвечают со смежных листов.
2. **Опциональный слой «модель-верификатор»** поверх гейтов — на остаток негативов без конкретики (слотless, юридические, бытовые). Решение владельца о сервере.
3. **Проверка первых трёх листов в гейтах**, а не только лидера: при смене порядка защита исчезает (так потерян отказ на e04 после веса Ф1.5).
4. **Принадлежность числа вопроса теме листа** — из-за веса specificity выдуманное число может случайно совпасть (clarify-полигон 10/10 → 4/10 после Ф1.5.0).

Порядок фаз: 0.3 (идентичность документа, применимость, слои base/supplement/change) → 4 (веб-сервис, PDF.js со ссылкой на лист) → 5 (API).

## Железные правила

- Цитата — дословный фрагмент листа; проверка машинная; нет цитаты — отказ.
- Никаких torch, transformers, sentence-transformers. Только `onnxruntime` + квантованная модель.
- Пустые листы — не мусор. SAFIR — штатная ВСУ, не признак мусора.
- Новые зависимости — только с разрешения владельца.
- Публичные контракты (CLI-коды, JSON schema v2, формат ссылок) без разрешения не менять.
- Один коммит на карточку, staging только явными путями, никаких `git add -A`.
- Сначала план и подтверждение, потом код. Сначала падающий тест, потом правка.
- Золотой набор аудируется до любых оптимизаций поиска (урок Ф1.2).

## Ловушки, влияющие на текущую работу

- Метрика отказа двусоставная: контроль ложных — по `refusal_false_on_found` (требование 0.00), доля обязательных — `refusal_on_miss`. Сводный `refusal_false` для контроля не использовать.
- `min_score = 0.35` бессмыслен: лидер OR-ветки всегда 0.8, порог не срабатывает никогда.
- Абляционные негативы на этой документации не работают: после скрытия эталонного листа система отвечает с соседних, проверка цитат проходит.
- Прогресс индексации мерить числом записей (`pages_without_vectors`), не размером файла базы (WAL колеблется).
- `_print_text` читает store (`is_continuation`): печать до `store.close()`, иначе `ProgrammingError` на ответе с парой соседних листов.
- Константы `tests/test_golden_metrics.py` должны соответствовать числу вопросов (45: 16 explain / 11 fault / 18 procedure).
- Файлы проекта UTF-8; консоль Windows показывает кириллицу как cp866 — искажение отображения не порча файла.
