## Диагноз (почему векторный канал не меняет метрики)

1. Семантика подмешивается ПОСЛЕ лексических фрагментов (`hybrid_search` дописывает векторные листы в хвост), а ответ строится из первых пяти — при непустой лексике векторные листы в топ-5 не доходят; лексика с триграммами находит что-то почти всегда.
2. Канал жив и честен: для «рабочего давления масла» лист 38 присутствует в векторной выдаче (cos 0.886).
3. Отказ не работает: косинусы не разделяют классы — корпусные 0.80–0.91, внекорпусные до 0.817; порог 0.18 не отрезает ничего; гейт «лексика нашла» открывается мусорными триграммными хитами.

Проверка эталонов промахнувшихся вопросов на сдвиг нумерации: промахов 22; у 11 ожидаемый лист того же документа стоит в топ-5 на 1–3 листа от найденного (e02, e03, e13, e15, e16, e18, p17, p19, p26, p27, p29 — вероятный сдвиг номера листа между изданиями PDF); у 11 (e04, e06, e07, e08, e09, e10, e14, p21, p24, p25, p28) ожидаемый документ в топ-5 отсутствует вообще (в т.ч. кластер из 6 вопросов с ожиданием листа 23 Редуктора ВР-14).

## Железные правила

- Цитата — дословный фрагмент листа, проверка машинная, нет цитаты — отказ.
- Коды завершения CLI: 0 / 1 / 2.
- Никаких torch, transformers, sentence-transformers. Только onnxruntime плюс квантованная модель.
- Пустые листы — не мусор. SAFIR — штатная ВСУ, не признак мусора.
- Новые зависимости — только с разрешения владельца.
- Публичные контракты (CLI, JSON schema v2, формат ссылок) без разрешения не менять.
- Один коммит на карточку, staging только явными путями, никаких `git add -A`.
- Сначала план, подтверждение, потом код. Тест падает — потом правка.
