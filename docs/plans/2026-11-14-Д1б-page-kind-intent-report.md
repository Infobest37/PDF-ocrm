# Д1б: интент вопроса ↔ тип листа и поиск по чертёжному номеру

Дата: 14.11.2026. База: `graph.db` (13 700 листов, разметка Д1а `--write`).

## Что сделано

1. **Интент вопроса** (`pdfgraph/page_kind.py`): `question_intent` различает
   семь интентов с приоритетом от конкретного к общему:
   `поиск_карты > обозначение > дефект > процедура > значение > назначение >
   неполный`.
   - «что такое» + параметр = `значение`; «что такое МУ-615» = `назначение`;
   - «как устроен/работает», «из чего состоит» = `назначение`;
   - `неполный` — только имя/код без вопросительного слова (иначе
     «как устроен автопилот» ошибочно уходил в уточнение);
   - строгий чертёжный номер: хотя бы одна точка, цифра до первой точки,
     плюс компонент из 4+ цифр / буква / дефис. Отсекаются `13,5`,
     `2.3.16`, `072.00.00`, `2024.11.14`; стандарты `ГОСТ/ОСТ/ТУ`
     распознаются отдельно.
2. **Вердикт по типу листа** (`pdfgraph/answer.py`, `page_kind_verdict`):
   - лидер нужного типа — ответ не меняется;
   - нужный тип в топ-10 — лист поднимается (`promote`), `Claim.evidence`
     пересчитывается, экстрактивные claims сортируются под нового лидера;
   - `назначение`: каталог, титул и содержание не могут быть лидером. Если
     подходящего листа нет — ответ выдаётся с пометкой
     `Answer.page_kind_missing` («Описания назначения не нашёл. Ближайшее —
     <тип>, лист N»), это не пустой отказ;
   - отказ — только когда требуемого типа нет во всём корпусе
     («листов типа … в базе нет»);
   - `значение` не переставляет выдачу (лидера-значение выбирает Ф1.29,
     норму проверяет Ф2.10); три допустимых типа — purpose, techcard, table;
   - `неполный` — уточнение: 3–5 разных типов листов и последний вариант
     «▸ Ни один не подходит — уточнить вопрос»;
   - неразмеченная база (`page_kind` пуст) — правило молчит, поведение
     прежнее.
3. **Каталог** (`pdfgraph/catalog.py`): `catalog_pairs` разбирает лист
   каталога (OCR по ячейке на строку) в пары «обозначение — наименование»;
   `lookup_catalog` ищет только по листам `page_kind = 'catalog'` в обе
   стороны и возвращает дословный срез листа. Не найдено — «в каталоге не
   нашёл». Строгий номер/стандарт без каталожной пары остаётся обычным
   поисковым ключом по всему корпусу (приёмочный `869309.001-03` не сломан).
4. **Показ пометки**: `Answer.page_kind_missing` печатается CLI (текст и
   JSON) и отдаётся веб-сервисом; `_print_json` переведён на `_safe_print`
   (символ «▸» не кодируется в cp1251).

## Не сделано и почему

- Лист 726 не поднят на контрольном вопросе: это ранжирование (Д3), карточка
  Д1б запрещает чинить его здесь.
- Классификатор Д1а не исправлен: листы 138/150/156 размечены неверно,
  это Д1в.
- Слой «модель-верификатор» не подключался: решение владельца отдельно.

## Замечено попутно, не правил

- `explain_display` для лидера-каталога строит абзац из шапки таблицы
  каталога; показ не входит в Д1б.
- `page_kind_missing` печатается CLI и отдаётся вебом, но GUI-окно его пока
  не показывает: поле аддитивное, подключение — отдельной задачей.

## Риски

- `lookup_catalog` ищет по `pages_fts.body` с `LIKE`: на 13 700 листах это
  миллисекунды, но при росте корпуса запрос станет дороже; при необходимости
  — отдельный индекс по каталогу.
- Правило «каталог/титул/содержание не лидер» включено только для
  `назначение`; для `процедура`/`дефект` запрет не проверялся.
- Разметка Д1а остаётся источником ложных типов; до Д1в правило назначения
  может выдавать пометку там, где описание есть, но помечено `other`.
