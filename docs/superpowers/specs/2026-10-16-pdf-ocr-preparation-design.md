# Дизайн: программа подготовки PDF-документов (Проект 1)

Дата: 2026-10-16
Статус: черновик на согласование

## 1. Зачем это делается (intent и почему)

Человеку нужно быстро находить нужную информацию в большом объёме авиационной
технической документации (сейчас — по вертолёту Ми-8МТВ), чтобы работать
качественнее. В дальнейшем на «подготовленные документы» сядет отдельный
**агент-инженер**, который должен отвечать своими словами, но **доказывать каждое
утверждение ссылкой на конкретный лист документа** и на технологические карты и
рисунки. В авиации точность по документации критична, поэтому выдумки
(галлюцинации) агента недопустимы.

Этот проект (Проект 1) — **только подготовка документов**. Агент-инженер — отдельный
проект (Проект 2), который будет работать **только с уже готовыми документами**.
Делаем поэтапно.

Ключевой вывод из обсуждения: «подготовленные документы» — это не просто PDF с
текстовым слоем. Нужно сохранить **структуру**: привязку текста к листам, таблицы
как данные, рисунки как опись, и всё это — в иерархии «система → подсистема».
Именно это (а не векторный поиск) не даёт таблицам «рассыпаться»: заказчик
сознательно **отказался от векторного подхода**, потому что вектор «рвёт» таблицы и
ответы получаются некорректными.

## 2. Что уже есть (текущее состояние и факты)

Приложение в репозитории: `pdf_ocr_app.py` (GUI на PyQt5) и `pdfocrm.py`
(консольный скрипт). Оно **не портативно**: зависит от отдельно установленных
Python, PyQt5, `ocrmypdf`, Tesseract (`C:\Program Files\Tesseract-OCR\`), poppler, а
`ocrmypdf` требует ещё и Ghostscript.

Папка `pdfs` — первый «боевой» набор для Ми-8МТВ: **49 PDF**. Замеры (по первой
странице, ориентировочно):

- **20 файлов — «сырые», ещё не обработанные.** Многие высокого разрешения
  (≈508–1143 DPI и выше), это фактически исходники.
- **29 файлов уже проходили OCR** (в метаданных `OCRmyPDF 16.10.4 / Tesseract 5.5.0`,
  producer `pikepdf`). У них картинка скана внутри лежит на **~150 DPI** (часть
  128–148, один 70). Это **физический потолок** качества для повторного распознавания
  из самого файла.
- Часть «OCR»-файлов (≈10) на первой странице вообще без растровой картинки — похоже,
  это изначально **цифровые** документы с настоящим текстом.
- Встречаются дубликаты/пары копий одного документа (напр. `РТЭ … кн.7` дважды).

Разбор конкретного файла `Каталок деталей и сборочных едениц Доп. к каталогу
Ми-8МТВ-1.0000.00.КД.Д-1701 … 22217 22562.pdf` (173 стр., ~4,9 МБ):

- Каждая страница — растровая картинка (изображения покрывают ~200% площади) с
  невидимым текстовым слоем (шрифт `GlyphLessFont`).
- Текстовый слой тонкий и неровный: покрытие обычно 3–10% площади; на «табличных»
  страницах распознано лишь ~130–160 символов (похоже, только колонтитул), т.е.
  **содержимое таблиц не распознано**.
- Глазами таблицы читаемы, но OCR выдаёт мусор и путает буквы: `Ми-8МТВ-1` →
  `Mu-8MTB-1`, `8МТ.6101.100` → `8MT.6101.100`.
- Самые «бедные по тексту» страницы оказались **пустыми листами / заставками /
  разделителями**, а не таблицами.

## 3. Доменная модель (как устроены документы)

- Документы — **отсканированные листы**, снятые подряд.
- **Пустой лист = граница.** После окончания технологической карты или раздела идёт
  пустая страница — так видно, что карта/раздел закончились. Это **не дефект**, а
  структурный маркер.
- **Коды в колонтитулах — это системы и подсистемы вертолёта:**
  - система: `XX.00.00`, например `023.00.00` = «Связное оборудование»;
  - подсистема: `XX.YY.ZZ`, например `023.11.30` = «АВАРИЙНЫЙ ПЕРЕНОСНОЙ РАДИОМАЯК
    ПАРМ-406А».
  - По этим кодам идёт поиск по книжкам; разграничение — **по подсистемам**.
- Коды системы и подсистемы стоят **на каждой странице** (в колонтитуле); номер листа
  («Стр. N») для навигации **не используется**.
- **Таблицы** (технологические карты, каталоги) содержат: номер рисунка, номер
  позиции, обозначение детали (напр. `8МТ.6101.100`), наименование, количество,
  сведения о взаимозаменяемости; есть ссылки на другие системы/рисунки, напр.
  «см. 028.10.00, рис. 1».
- **Рисунки/схемы** имеют номер рисунка и относятся к системе/подсистеме.

Итоговая «несущая конструкция» подготовленных данных:
**система → подсистема → листы → таблицы → рисунки.**

## 4. Цели (что должна делать программа)

1. **Портативность.** Папка с программой копируется на любой Windows-ПК и
   запускается **без установки**. Движок OCR и языковые модели (рус+англ) лежат
   внутри папки.
2. **Пакетная обработка.** Обрабатывает папку со сканами целиком. Рассчитана на
   **любые подобные** документы, не только на Ми-8МТВ (дальше будут другие типы
   вертолётов, приходящие как необработанные PDF).
3. **Качественное распознавание.** В первую очередь **таблиц/техкарт/каталогов** и
   мелкого шрифта. Исправление путаницы кириллицы и латиницы.
4. **Сохранение структуры:**
   - система/подсистема — по кодам в колонтитулах;
   - границы технологических карт — по пустым листам;
   - таблицы — как данные (строки/колонки/значения) с привязкой к листу;
   - рисунки/схемы — как **опись**: номер рисунка + система/подсистема + лист
     (полное «понимание» схем — задача Проекта 2).
5. **Результат:**
   - PDF с полным рабочим текстовым слоем (поиск и выделение текста работают);
   - **отдельные структурированные данные** «система → подсистема → листы → таблицы →
     рисунки» для будущего агента.
6. **Контроль качества с эскалацией:**
   - оценивает, где распознавание **ненадёжно**;
   - применяет усиленную обработку;
   - если не помогло — **показывает эти страницы человеку**; человек пересканирует их
     в лучшем качестве и присылает; программа подставляет новые сканы и переобрабатывает.

## 5. Не-цели (в этом этапе не делаем)

- Сам агент-инженер, ответы на вопросы, чат, «понимание» схем.
- Векторный поиск как основу (отвергнут).
- Гарантию идеального распознавания там, где исходник физически не содержит деталей
  (уже обработанные файлы на ~150 DPI).

## 6. Анти-цели (что считается провалом, даже если «работает»)

- Данные, искажающие документ (неверные буквы/значения), из-за которых будущий агент
  ответит неправильно.
- Пустые листы, помеченные как дефекты/ошибки скана.
- Потеря структуры (таблицы, «сплющенные» в текст; потеря привязки к листу/системе).

## 7. Ограничения

- Только **Windows**, запуск **без доустановки**, одна переносимая папка.
- Языки: **русский + английский**.
- Опора на уже имеющиеся файлы; докачивание — **только точечно**, по эскалации.
- ~29 уже обработанных файлов ограничены ~150 DPI.
- Нужны **все** книги без исключения.

## 8. Что уже решено человеком (не оспаривается)

- Делать **отдельные структурированные данные**, а не только PDF.
- **Пустые листы = границы**, не дефекты.
- **Коды = системы/подсистемы**; поиск по ним.
- Этапность: сначала подготовка документов, агент — потом.
- Эскалация: человек вручную пересканирует проблемные страницы.
- Порядок источника: сначала максимум из имеющегося файла; оригинал — только если
  место всё равно читается неверно.
- У человека **есть доступ к бумажным оригиналам**, он может пересканировать любую
  проблемную страницу в лучшем качестве и прислать.
- **Ключ навигации и структуры — коды системы/подсистемы**, они есть на каждой
  странице; номер листа для навигации не используется.
- **Форма замен:** человек присылает либо отдельные сканы страниц (программа заранее
  сообщает, какие страницы нужны), либо целый оригинальный PDF.
- **Приёмка — выборочная:** человек вручную проверяет лишь несколько страниц каждого
  типа документов (не все 10 000+).
- **Справочник кодов:** файл `Коды систем Вертолета.txt` в корне проекта (стиль
  ATA-100) — источник «код → название».

## 9. Что оставлено проектировщику/строителю (мои предложения, можно оспорить)

- Собрать всё внутрь папки: встроенный Tesseract + модели `rus`/`eng`; **отказаться от
  Ghostscript и poppler**; рендер страниц делать через PyMuPDF.
- Настроить OCR под таблицы/плотный текст (подбор режима сегментации, предобработка:
  выравнивание, шумоподавление, бинаризация; апскейл мелкого текста).
- Нормализация текста (регистр, `ё`/`е`, исправление homoglyph-ошибок кириллица/латиница).
- Формат структурированных данных (напр. JSON или SQLite) и его схема.
- Автоопределение границ технологических карт и извлечение кодов систем/подсистем.
- Способ запуска пакетной обработки (GUI, консоль или оба) для портативной сборки.
- Метрика «надёжности» распознавания по странице и форма представления проблемных
  страниц человеку для пересканирования.
- Схема структурированных данных и что считать «единицей» (страница, карта, таблица);
  предложение: единица — **лист**, карта/таблица — сущности, привязанные к листам.
- Интерфейс запуска: предложение — консольный запуск по папке как ядро + (при
  необходимости) простой GUI поверх; сначала достаточно консоли.
- **Цифровые страницы/файлы** (с родным текстом): сохраняем родной текстовый слой,
  OCR применяем только к растровым страницам (решение по-странично/по-файлово).
- **Обобщаемость:** сначала доводим Ми-8МТВ, но правила (коды, границы карт)
  реализуем **конфигурируемыми**, а не зашитыми, чтобы принять другие типы.
- **PDF на выходе:** сохраняем визуальную достоверность скана (без ухудшающего
  сжатия); текстовый слой делаем полным и поисковым, **включая таблицы**;
  авторитетный источник данных таблиц — структурированные данные.
- **Формат замен при пересканировании:** принимаем и отдельные изображения страниц, и
  пере-экспортированный PDF; сопоставляем по номеру листа.
- **Коды → названия:** храним коды; названия систем/подсистем берём из текста
  документов; внешний справочник — только если заказчик его предоставит.
- **Ресурсы:** пакет обрабатывается за приемлемое время на обычном офисном ПК без GPU
  (напр. пакетно, ночью); тяжёлый апскейл применяем точечно к сложным страницам.
- **Справочник кодов:** парсить `Коды систем Вертолета.txt`: `XX.00.00` → название
  системы, `XX.YY.00` → название секции; третий уровень (`XX.YY.ZZ`) — хранить код как
  есть, название брать из текста документа.
- **Части и дубликаты:** обрабатываем каждый файл независимо (нужны все книги);
  объединение логических документов не делаем — структура всё равно собирается по
  кодам систем/подсистем, так что страницы одного кода естественно группируются.

## 10. Открытые вопросы

Разрешены (см. раздел 8): источник и форма замен, выборочная приёмка, ключ навигации
по кодам систем/подсистем, наличие справочника кодов. Открытых вопросов к заказчику
не осталось.
